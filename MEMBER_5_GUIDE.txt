4. YOUR EXACT CODE FILES & WHAT THEY DO
--------------------------------------------------------------------------------
📍 config/OpenApiConfig.java
   - Configures SpringDoc OpenAPI 3:
     1. Defines the OpenAPI info metadata (Title, Version 1.0, Description).
     2. Configures the JWT Bearer Security Scheme:
        @SecurityScheme(name = "BearerAuth", type = SecuritySchemeType.HTTP, scheme = "bearer", bearerFormat = "JWT")
     3. Adds global security requirements so developers can click "Authorize" in 
        Swagger UI and test protected routes directly in the browser.

📍 src/test/java/.../service/BidServiceTest.java
   - Rigorous unit test suite validating the live bidding engine:
     1. testPlaceBid_Success: Asserts valid bid updates player price and persists bid.
     2. testPlaceBid_InsufficientBudget: Asserts RuntimeException when bid exceeds team budget.
     3. testPlaceBid_ConsecutiveBiddingFromSameTeam: Asserts RuntimeException when team tries to outbid itself.
     4. testPlaceBid_BelowCurrentHighestBid: Asserts RuntimeException when bid is <= highest bid.
     5. testPlaceBid_BelowBasePrice: Asserts rejection when first bid is lower than player base price.

📍 src/test/java/.../service/PlayerServiceTest.java
   - Comprehensive unit test suite for squad management:
     1. testSellPlayer_Success: Asserts player is marked SOLD and budget is deducted.
     2. testSellPlayer_ExceedMaxSquadLimit: Asserts failure when team has 25 players.
     3. testSellPlayer_ExceedMaxOverseasLimit: Asserts failure when team has 8 overseas players.
     4. testSellPlayer_InsufficientBudget: Asserts failure when team cannot afford player.
     5. testMarkUnsold_RefundsBudget: Verifies that marking a sold player UNSOLD refunds team purse.

📍 postman/IPL_Auction_System.postman_collection.json & IPL_Auction_Environment.json
   - Full REST test collection with pre-request scripts and automated assertions (pm.test):
     1. Authentication: Login (Admin & Team Owners) -> Automatically saves jwt_token variable.
     2. Team Management: GET /api/teams, POST /api/teams, budget assertions.
     3. Player Management: GET /api/players, PUT /api/players/{id}/sell.
     4. Bidding Engine: POST /api/bids, concurrent bid verification.

📍 .github/workflows/ci.yml

9. TOP MENTOR QUESTIONS & HOW TO ANSWER CONFIDENTLY
--------------------------------------------------------------------------------
Q1: What does your GitHub Actions CI workflow do on every pull request?
Ans: The CI pipeline runs inside an isolated ubuntu-latest container with JDK 17. It 
     checks out the codebase, restores the Maven dependency cache, compiles the application, 
     and executes all JUnit 5 test suites via ./mvnw clean test. If any single test fails or 
     a compile error occurs, the pull request status is marked red and merging is blocked.

Q2: Why did you use Mockito instead of running tests against a live MySQL database?
Ans: Unit tests must be ultra-fast, deterministic, and isolated. Using Mockito allows us to 
     mock repository interactions (like playerRepository.findByIdForUpdate()) in-memory in 
     milliseconds without requiring an active MySQL instance or network connectivity, while 
     verifying method interactions with verify().

Q3: What critical bidding edge cases are covered by your tests?
Ans: In BidServiceTest, we assert:
     1. testPlaceBid_InsufficientBudget: Bids exceeding current team purse fail.
     2. testPlaceBid_ConsecutiveBiddingFromSameTeam: Consecutive bids by the same franchise are blocked.
     3. testPlaceBid_BelowCurrentHighestBid: Bids equal to or lower than the active bid are rejected.
     4. testPlaceBid_BelowBasePrice: First bid below the player's base price is rejected.

Q4: How does Swagger UI support testing JWT-protected endpoints?
Ans: In OpenApiConfig.java, we declare a SecurityScheme of type HTTP Bearer format JWT. 
     This renders an 'Authorize' padlock button in Swagger UI. Developers authenticate via 
     /api/auth/login, copy the token into Swagger's Authorize dialog, and Swagger automatically 
     attaches the Authorization: Bearer <token> header to all subsequent interactive API tests.
